Purpose
Herewith the specifications with which the CubeWatchTS Nord Pool standard interface has been developed are documented. The task of the Nord Pool interface is to capture the available data in the API interface of Nord Pool in terms of Intraday Orders and Trades prior to their physical delivery.
The intraday markets are open 24/7, 365 days a year offering 15-minute, 30-minute, hourly and block products.
High Level Architecture Diagram
Design
There are three major components in the design.
API Connector– Reads messages from Nord Pool API using STOMP protocol through WebSocket connection and saves the data from subscribed topics to parquet file per contract.
Parser – Parses data from the API connector in the parquet files(only for contracts with private orders and trades if “IsProcessingOnlyRelevantContracts” flag is set) and maps them to order and trade data structures and pushes them to order and trades parquet files to be pushed to database.
Persist – Reads the orders and trades parquet files and persists them to the database.

SockJs Implementation
1. Compose the Intraday API endpoint address in form of /user/{serverId}/{sessionId}/websocket 
user is the URL of the endpoint.
ServerId is a client-generated random number between 000-999 presented in the 3-digit form.
SessionId is a client-generated random string unique for each session. Use the length of 10-20 symbols.
SockJS server emits messages that start from "frame letter", in relevant cases followed by the payload of the frame. From the SockJS protocol description:
o - Open frame. Every time a new session is established, the server must immediately send the open frame. This is required, as some protocols (mostly polling) can't distinguish between a properly established connection and a broken one - we must convince the client that it is indeed a valid URL and it can be expecting further messages in the future on that url.
h - Heartbeat frame. Most loadbalancers have arbitrary timeouts on connections. In order to keep connections from breaking, the server must send a heartbeat frame every now and then. The typical delay is 25 seconds and should be configurable.
a - Array of json-encoded messages. For example: a["message"].
c - Close frame. This frame is sent to the browser every time the client asks for data on closed connection. This may happen multiple times. Close frame contains a code and a string explaining a reason of closure, like: c[3000,"Go away!"]
SockJS client does not have to use any "frame letters":
SockJS server does not have any framing defined. All incoming data is treated as incoming messages, either single json-encoded messages or an array of json-encoded messages, depending on transport. For our case, please see section 3 below.
2. Open a Websocket connection to the Intraday API endpoint.
After a successful connection, the server will send back an o frame. Once it is received, you can consider connection confirmed.
Depending on the version of SockJS on the server side, the server will also send heartbeat frames h. The server sends these frames to keep the connection alive. This can be ignored on the client's side.
3. Messages received from the server are a-denoted frames. The payload of the message is a JSON array with an escaped string inside (a STOMP packet, in our case). An example of a SockJS coded STOMP message with some headers and JSON payload: 
a["MESSAGE\\ncontent-length:232\\n\\content-type:application/json\\n\\n{\"property\":\"value\"}\u0000"]
4. Messages sent to server should be:
converted to a JSON string - with escaped special character representation and appended by \u0000 symbol.
then wrapped in a JSON array.
For example, for sending the STOMP Connect command, the SockJS+STOMP message will look like: 
["CONNECT\\nX-AUTH-TOKEN:token\\n\\n\u0000"]
API Description
The API uses a subscription model based on “topics”. To receive a particular kind of information, the user subscribes to a necessary topic that may include variable parameters. All subscription topics are independent and can be used simultaneously as soon as the subscription is permitted. To re-subscribe, the user must execute STOMP UNSUBSCRIBE and SUBSCRIBE again.
API uses a subset of commands from the STOMP protocol.
After a successful subscription, data streaming to the client will commence. All subscription streams follow the same convention of sending first a “snapshot” of the current data. Subsequent changes are then sent in the form of “deltas” when only the information that has changed is distributed.
STOMP headers of most messages contain an x-nps-snapshot field that may be true or false, indicating that the message contains respectively snapshot or delta. If this field is absent, the message should be regarded as delta.
The backend may send a full snapshot between delta messages, although we expect a seldom need for this. When this occurs, the client should overwrite all previously persisted data from the subscription with the information received from the new snapshot.
All messages are encoded in JSON format.
Optionally, the user can choose to use compressed format for messages, that is simply done by adding /gzip suffix to a subscription topic. Then, the payload of the message will be pre-compressed using gzip and base-64 encoded, so the client should perform a de-compression. 
Client (user) can log in maximum 10 times per twenty seconds and not more than 20 times per twenty minutes. The limit is per username.
Most subscriptions come in two types:
Conflated – we generate new deltas every 0.25 seconds. All updates received during this interval are sent as one message. If several updates happen to the same entity, only the latest state is provided. Generates less load on a client but increases the latency.
Streaming – all individual updates are sent immediately. A client should be able to handle this traffic.
Each message will be enriched with a topic-specific sequence number so that the client can easily follow up on any missed messages. It is stored in x-nps-sequenceNo STOMP header. The topic-specific numbering means, that if two instances of a client subscribe at a different time to the same topic, they will receive the same delta sequence numbers, as deltas are broadcast to all topic's subscribers simultaneously.
An additional check must be made by comparing the observed x-nps-sequenceNo with the information provided by the /heartbeatping subscription. If either check fails, it is strongly recommended to unsubscribe and re-subscribe to the topic to receive fresh snapshots to guarantee that the received data remains consistent.
Login and Logout
Communication with the API happens within a WebSocket/STOMP session.
To start/end the session the client needs to log in/log out. SSO Server provides unique Authorization Token for each user. Basic Authentication to SSO Server is required that uses clientId and clientSecret properties. 
To remain connected continuously, the authentication token must be updated before its expiration time.
During the session, Heartbeat ping messages will be sent every 15 seconds from the server to allow message sequencing checks.
The initial step in connecting to a server is to obtain an authentication token. 
SSO endpoint: https://sts.test.nordpoolgroup.com/connect/token
Shell authentication: 
curl -k -H "Authorization: Basic Y2xpZW50X2ludHJhZGF5X2FwaToxeEI5SWsxeHNFdTJuYndWYTFCUg==" -H "Content-Type:application/x-www-form-urlencoded" -X POST -d "grant_type=password&scope=auction_api&username=[USERNAME]&password=[PASSWORD]"  https://sts.nordpoolgroup.com/connect/token
The user must then use STOMP CONNECT to connect to the server and log in. Login and password are not required. Instead, a custom STOMP header field X-AUTH-TOKEN must contain the authentication token.
An authentication token has a finite period of validity. Once it expires, the client is disconnected. In order to keep connection uninterrupted, you should obtain a new token before the old one expires and perform a token refresh, so the new token's validity period will be in effect.
The current expiration time of a token is 60 minutes.
To perform SSO token refresh client should:
1) Obtain a new token from SSO via the same REST call.
2) SEND the following message to //command topic:
{
"type":"TOKEN_REFRESH",
"oldToken":"HUGE_STRING_OLD_TOKEN",
"newToken":"HUGE_STRING_NEW_TOKEN"
}
Where "HUGE_STRING_OLD_TOKEN" and "HUGE_STRING_NEW_TOKEN" denote the actual tokens, old and new.
To log out, a client should SEND the following message to //command topic:
{  
   "type":"LOGOUT"
}
Units
The trading unit quantity in Nord Pool’s Intraday Platform is kW (kilowatt).
Currencies are quoted in minor currency units (Euro cents, pence) – this means there are no decimals used and prices should be submitted as integer values.
Euros should be expressed in cents; to submit an order for 1.50 EUR the price value submitted via the API should be 150.
UK Pounds should be handled as pence; for an order of 4.75 GBP the value should be 475.
Date and Time: all dates and times used in the API messages are in ISO 8601 format and always UTC (ZULU) time indicated by 'Z' in the end of the timestamp, e.g.: 2016-12-13T11:08:35Z
Countries: use ISO 3166-1 alpha-2 format.
Currency: use ISO 4271 format.

Business Process
Login / TokenRefresh
Token refresh worker connects to Nord Pool’s rest endpoint to get the token and pushes it to the in-memory queue. It gets a new token every time it exceeds the configurable token refresh time.
The API Connector waits until it gets the token from the Token Queue and sends a WebSocket connection request to Login to Nord Pool WebSocket endpoint. It receives a Connected message from Nord Pool once the connection is successful.
API Connector also sends a TokenRefresh message whenever the token queue sends a new token.

Subscription
Once we receive configuration information, we send a Subscribe message to several topics of interest.
On a successful subscription we start receiving messages for that subscription which we push to in memory queue to not hold the next message till we process this message.
We have a worker that reads from the in-memory queue and writes it to parquet files.
Parser reads from the above parquet files parses the data and creates a zip file with orders and trades parquet files. Persist service reads the zip files and dumps the data into the database.
Subscription message will be in the below format for respective topic.
/user/<username>/<version>/<streaming>/<topic>/<areaId>
On subscription the initial message is a snapshot and further message we receive the deltas.
For snapshot messages for orders and trades we send the snapshot flag to remove the duplicates while parsing the data.
Subscriptions
/configuration – Current API users configuration information
/localview – Public orders
/orderExecutionReport – Private orders
/ticker – Public trades
/privateTrade – Private trades
/contracts – Open contracts information 
/deliveryAreas – Delivery areas information
/heartbeatping – To get heartbeat information for above subscriptions
Logout / Reconnection / Error handling
We send a Disconnect STOMP message (Logout message) through the WebSocket connection when the adapter is stopped and close the WebSocket connection.
If any process in adapter fails, it waits for a minute and tries reconnecting again and followed by resubscribe on successful connection.
While parsing the messages if there is a failure and the application stops, we can reprocess the data for that day as mentioned in the operations guide.
We send a resubscribe message for a specific topic when there is a sequence mismatch while receiving the messages in API connector.
Handshake
We write a handshake once the persist service saves the data for a day.
If we must rerun data for a day, we must delete the entry from CLIENT_HANDSHAKE table and rerun the data for the day.

Following in this chapter, a brief explanation of all the different subscriptions used by the Nord Pool adapter and their data structure.
/configuration
The Configuration topic is used to receive user's authorization and permission details and subsequent updates on these. The configuration message contains the list of allowed portfolios, market areas, and throttling limits. Access rights are time-dependent and both portfolios and areas have time-based validity restrictions.
Should user rights have changed, a new set of rights will be distributed via the topic, replacing any previous rights. All attempts to use portfolios and areas that are not in the list will be ignored by the server.
Subscription topic: /user/<username>/<version>/configuration
Configuration subscription does not use // part of the subscription topic.

API users will get the report with an array of orders, which have State=PENDING. This orderState means that the order reached back-end and is about to be processed. Its purpose is to acknowledge the order reception as in some cases actual order processing, such as in XBID, may take some time.

/privateTrade
User's so-called "own" trades, that is, the trades from the same company for the portfolios that user has access to.

A user has access to one or more portfolios. The convention is that /privateTrades receives all trades made with same portfolios that user has access to.

Delivery Period Mapping for Orders
The delivery period field is obtained using the fields deliveryStart and deliveryEnd (converting data always in CET/CEST). The timings are then mapped to hours, quarter hours and block of those, according to what available in the CubeWatchTS data structure as per below. If the delivery date is the same day as the transaction date, the DELIVERY_PERIOD will start with “C”, else it will start with “N”. Timings for the split are based on CET/CEST time zone and the productTypes will be mapped as following:
P15 – CQ/NQ
P30 – CQB/NQB
P60 – CH/NH
Custom block –CHB/NHB or CQB/NQB
Remaining pre-defined blocks CHB/NHB
The hourly instruments (P60, custom hourly blocks and per-defined blocks) will follow the syntax:
- CH<hour> or NH<hour> for non-blocks instruments 
- CHB<start_hour>-<end_hour> or NHB<start_hour>-<end_hour> if it is a block and start and end time are on the same day
- CHB<start_hour>-NHB<end_hour> if it is a block and start and end time are not on the same day
The quarter-hourly instruments (P15, P30 and custom quarterly blocks) will follow the syntax:
- CQ<hour><quarter> or NQ<hour><quarter> for non-blocks instruments 
- CQB<start_hour><start_quarter>-<end_hour><end_quarter> or NQB<start_hour><start_quarter>-<end_hour><end_quarter> if it is a block and start and end time are on the same day
- CQB<start_hour><start_quarter>-NHB<end_hour><end_quarter> if it is a block and start and end time are not on the same day
<hour> are all values included in 00-23 and <quarter> are all values included in q1-q4.
Examples:
deliveryStart = current day 15:00 CET, deliveryEnd = current day 16:00 CET -> CH15
deliveryStart = current day 15:00 CET, deliveryEnd = current day 17:00 CET -> CHB15-16 
deliveryStart = current day 22:00 CET, deliveryEnd = next day 00:00 CET -> CHB22-23
deliveryStart = next day 15:00 CET, deliveryEnd = next day 15:15 CET -> NQ15q1
deliveryStart = current day 15:30 CET, deliveryEnd = current day 16:00 CET -> CQB15q3-q4
deliveryStart = current day 23:30 CET, deliveryEnd = next day 00:00 CET -> CQB23q3-q4
Volume Mapping for Orders
IF public:
IF cached and deleted, THEN = cached volume, 
ELSE = quantity/1000
IF private: 
IF PARTIAL_EXECUTION or FULL_EXECUTION and cached, THEN = cached quantity – quantity / 1000
   ELSE = quantity/1000

Edge cases description
Own data duplicates in public transactions
All public data is filtered - using the filter (order.Ownership == OrderOwnership.OTHER) - to determine whether the single public transaction comes from the own company. In case yes, this data is discarded, whether in the opposite case it is simply written in the database as usual.
Handling overnight orders
End of day process for previous day is triggered when we get an order for the new day. At the end of the day, we close all the existing overnight orders.
The created cancelled order has TRAN_STATUS = C and Datetime: 23:59:59:999 CET/CEST (D-1)
Handling of hibernation events
In hibernation events, the following approach is used: the hibernation (USER_HIBERNATED and SYSTEM_HIBERNATED events) are translated into a cancellation event. When the order is reactivated, this is recorded as an update event, with TRAN_STATUS = A. The order ID and all the other related fields remain unchanged.
Handling duplicated data in XBID orders
We have a flag called “LoadXbidPublicOrders” in the configuration file. If set to false, it gets the public XBID order for only one delivery area (which ever delivery area data comes first). If set to true, it will get all the public XBID orders.
Handling public trades
If we have multiple legs and both have different delivery areas, we write both trades. 
If we have multiple legs with different delivery areas, then we choose the alternate legs between buy and sell based on the previous public trade.
If we have a single leg, we write that trade.
Parquet Files
High level overview
Nord Pool interface uses parquet files to store the data to the file system. 
API Messages
The API messages are stored in the format below for each subscription.
Contracts – yyyy-mm-dd-contracts.parquet
Delivery areas – yyyy-mm-dd-delivery-areas.parquet
Private orders – yyyy-mm-dd-private-orders-ContractId.parquet (we will have one file for each contract that is traded)
Public orders – yyyy-mm-dd-public-orders-ContractId.parquet (we will have one file for each contract that is traded)
Private trades – yyyy-mm-dd-private-trades-ContractId.parquet (we will have one file for each contract that is traded)
Public trades – yyyy-mm-dd-public-trades-ContractId.parquet (we will have one file for each contract that is traded)
Parsed Data
Parser steps
Parser gets the data for the previous day from the previous day's parquet files and populates the cache.
Parses run days contracts one by one maintaining the above cache per contracts scope and does the mapping.
Creates a persist file as mentioned below per contract and order or trade.
The parsed data is stored in zipped folder in the format yyyy-mm-dd.zip, which contains the data in the format below.
Orders – CLIENT_ORDERS_ContractId.parquet (One file for orders from each contract)
Trades – CLIENT_TRADES_ContracId.parquet (One file for trades from each contract)
